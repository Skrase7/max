# Контракты API бэк и фронт

Статус черновик
Чат и сообщения будут в отдельном разделе
Пространства проекты и участники тоже отдельно

| Раздел | Состояние |
|---|---|
| Профиль и настройки | контракт и swagger схема. Ручек пока нет |
| Канбан | только контракт. Ручек пока нет |

Swagger схема лежит рядом в `apps/backend/docs/openapi.yaml`
Посмотреть ее можно на editor.swagger.io через File и Import file
Ручка `/task` в бэке это тестовая заглушка. Канбан ее заменит

## Общие правила

* Базовый URL `/api/v1`
* Авторизация через заголовок `Authorization: Bearer <token>`
* Поля в camelCase
* Значения enum в snake_case
* id это UUID строкой
* Дата без времени это строка вида `2026-11-20`
* Момент времени это ISO 8601 в UTC вида `2026-11-13T12:00:00Z`
* Один юзер на все пространства. Профиль общий
* Создание отвечает 201. Все остальное 200

### Успешный ответ

```json
{ "result": {} }
```

Список с пагинацией

```json
{ "result": { "items": [], "nextCursor": "c2VjcmV0" } }
```

Длинные списки отдаются частями
Вместе с частью приходит `nextCursor`
Чтобы получить следующую часть фронт шлет его в параметре `cursor`
Остальные параметры запроса остаются прежними
Что внутри `nextCursor` фронту знать не нужно
Когда список закончился `nextCursor` равен `null`
Размер части задает `limit`
По умолчанию 50 и не больше 200
Неправильный `cursor` это ошибка 400

Номера страниц не используем
Пока юзер листает в список добавляют новые записи
С номерами страниц они сдвигали бы все остальное

### Ошибка

```json
{
  "code": "VALIDATION_ERROR",
  "message": "title must be shorter than 200 characters",
  "details": {
    "fields": [{ "field": "title", "message": "too long" }]
  }
}
```

`details` это всегда объект или `null`
Что внутри зависит от `code`

| Статус | code | Когда | details |
|---|---|---|---|
| 400 | BAD_REQUEST | запрос нельзя выполнить | `null` |
| 400 | VALIDATION_ERROR | поля не прошли валидацию | `{ fields }` |
| 401 | UNAUTHORIZED | нет токена или он протух | `null` |
| 403 | FORBIDDEN | доступ к проекту есть но прав на действие нет | `null` |
| 404 | NOT_FOUND | сущности нет или нет доступа к проекту | `null` |
| 409 | CONFLICT | данные устарели. Перечитать и повторить | актуальные данные |
| 429 | TOO_MANY_REQUESTS | слишком много запросов | `null` |
| 500 | INTERNAL_ERROR | ошибка сервера | `null` |

Чужой проект отвечает 404 а не 403
Так по ответу нельзя понять что проект существует
При 429 приходит заголовок `Retry-After` в секундах

### PATCH

Меняет только пришедшие поля
Явный `null` очищает поле
Не пришедшее поле не трогается

### Повтор запроса

Сеть может упасть после того как сервер уже создал задачу
Фронт повторит запрос и получится дубль
Чтобы этого не было есть заголовок `Idempotency-Key`

Фронт кладет в него случайный UUID
При повторе шлет тот же ключ
Сервер видит знакомый ключ и отдает прежний ответ
Второй раз ничего не создается
Ключ живет 24 часа

Заголовок работает на всех POST которые что то создают
Он необязательный

## Enum

| Enum | Значения | Примечание |
|---|---|---|
| Theme | `light` `dark` `system` | тема интерфейса. По умолчанию `system` |
| Language | `ru` `en` | язык интерфейса. По умолчанию `ru` |
| TimeFormat | `12h` `24h` | формат времени. По умолчанию `24h` |
| TaskPriority | `low` `medium` `high` `urgent` | по умолчанию `medium` |
| ColumnStatus | `todo` `in_progress` `review` `done` | системный статус колонки |
| ProjectRole | `admin` `member` | роль юзера в проекте |
| TaskHistoryAction | `created` `title_changed` `description_changed` `assignee_changed` `moved` `priority_changed` `due_date_changed` `blocked` `unblocked` `checklist_changed` `deleted` | тип записи в истории |
| TaskHistorySource | `user` `github` `system` | кто сделал изменение. Пока всегда `user` |

## Профиль и настройки

Сделано по примеру Slack
Там это два разных места
Профиль видят все
Настройки видит только сам юзер

Юзер один на все пространства
Поэтому профиль и настройки тоже одни

| Метод | Путь | Кто | Что |
|---|---|---|---|
| GET | `/users/me` | любой | мой профиль |
| PATCH | `/users/me` | любой | изменить профиль |
| GET | `/users/me/settings` | любой | мои настройки |
| PATCH | `/users/me/settings` | любой | изменить настройки |

Без токена все четыре отвечают 401

### Профиль

```json
{
  "result": {
    "id": "uuid",
    "email": "user1@example.com",
    "displayName": "Даня",
    "title": "Backend developer",
    "avatarUrl": null,
    "timezone": "Europe/Moscow"
  }
}
```

| Поле | Тип | Можно менять | Смысл |
|---|---|---|---|
| id | uuid | нет | id юзера |
| email | строка | нет | почта. Меняется через авторизацию |
| displayName | строка | да | имя которое видят другие |
| title | строка или `null` | да | должность |
| avatarUrl | строка или `null` | нет | аватар. Загрузка появится вместе с файлами |
| timezone | строка | да | часовой пояс вида `Europe/Moscow` |

`timezone` лежит в профиле потому что его видят другие
По нему же считаются рабочие часы и сроки задач

### PATCH /users/me

```json
{ "displayName": "Даня", "title": null, "timezone": "Europe/Moscow" }
```

Любые из этих трех полей
`title` можно очистить через `null`
`displayName` и `timezone` очистить нельзя. Ответ 400
`timezone` должен быть настоящим поясом из базы IANA. Иначе 400
Лишние поля сервер молча отбрасывает
Ответ профиль целиком

### Настройки

```json
{
  "result": {
    "theme": "system",
    "language": "ru",
    "timeFormat": "24h",
    "notifyTaskAssigned": true,
    "notifyTaskDueSoon": true,
    "notifyTaskBlocked": true,
    "dndUntil": null,
    "workHoursEnabled": false,
    "workDays": [1, 2, 3, 4, 5],
    "workHoursStart": "09:00",
    "workHoursEnd": "18:00"
  }
}
```

Настройки плоские без вложенных объектов
Так PATCH остается простым и каждое поле ложится на один контрол формы

| Поле | Тип | По умолчанию | Смысл | Контрол |
|---|---|---|---|---|
| theme | Theme | `system` | тема интерфейса | Radio |
| language | Language | `ru` | язык интерфейса | Select |
| timeFormat | TimeFormat | `24h` | как показывать время | Radio |
| notifyTaskAssigned | boolean | `true` | уведомлять когда мне назначили задачу | Switch |
| notifyTaskDueSoon | boolean | `true` | уведомлять когда срок моей задачи близко | Switch |
| notifyTaskBlocked | boolean | `true` | уведомлять когда мою задачу заблокировали | Switch |
| dndUntil | момент времени или `null` | `null` | не беспокоить до этого момента | Select с вариантами |
| workHoursEnabled | boolean | `false` | включить рабочие часы | Switch |
| workDays | массив чисел | `[1,2,3,4,5]` | рабочие дни. 1 это понедельник и 7 это воскресенье | Checkbox |
| workHoursStart | строка `HH:mm` | `09:00` | начало рабочего дня | Select |
| workHoursEnd | строка `HH:mm` | `18:00` | конец рабочего дня | Select |

У нового юзера настройки уже есть со значениями по умолчанию
GET никогда не отвечает 404

### Как работают уведомления

Три поля `notify...` это три события канбана из ТЗ
Назначение задачи приближение срока и блокировка

Не беспокоить работает как пауза в Slack
Пока `dndUntil` в будущем уведомления не приходят
Когда момент прошел сервер сам отдает `null`

Рабочие часы работают как расписание уведомлений в Slack
Если `workHoursEnabled` включен уведомления приходят только в рабочие дни и часы
Часы считаются по `timezone` из профиля
Вне расписания уведомления копятся в центре уведомлений без звука

Сами уведомления появятся позже
Сначала настройки будут только сохраняться

### PATCH /users/me/settings

```json
{ "theme": "dark", "dndUntil": "2026-11-20T18:00:00Z" }
```

Любые поля настроек
`dndUntil` можно очистить через `null`
Остальные поля очистить нельзя. Ответ 400
`dndUntil` должен быть в будущем. Иначе 400
`workDays` присылается целиком. От 1 до 7 чисел без повторов
`workHoursStart` должен быть раньше `workHoursEnd`. Иначе 400
Проверка идет по итогу после изменения а не только по пришедшим полям
Если хоть одно поле неправильное не сохраняется ничего
Ответ настройки целиком

### Что добавится в настройки позже

| Что | Когда |
|---|---|
| загрузка аватара | вместе с файлами и S3 |
| статус с эмодзи и текстом | вместе с чатом |
| уровень уведомлений все или только упоминания | вместе с чатом |
| уведомления для отдельных каналов и проектов | вместе с чатом |
| отправка сообщения по Enter | вместе с чатом |
| привязка телеграма и уведомления в бота | вместе с ботом |
| смена почты и пароля | вместе с авторизацией |

Новые поля будут только добавляться
Старые не переименовываем

## Как устроена доска

У каждого проекта одна доска
Доска состоит из колонок
В колонках лежат задачи

При создании проекта создаются 4 колонки

| Колонка | status |
|---|---|
| Нужно сделать | `todo` |
| В работе | `in_progress` |
| На проверке | `review` |
| Готово | `done` |

Колонки можно добавлять переименовывать удалять и переставлять
У каждой колонки есть системный статус
По нему работают фильтры и будущие автопереходы из GitHub
Несколько колонок могут иметь один статус
Статус задачи берется из ее колонки
Отдельно его не задают
Автопереход в статус кладет задачу в первую колонку с этим статусом

### Порядок задач

У задачи есть поле `position`
Это число. Может быть дробным
Чем меньше тем выше в колонке
Фронт сортирует по нему
Позицию считает сервер
Фронт присылает только соседа

### Номер задачи

У задачи есть `number`
Он растет внутри проекта 1 2 3
Номер не меняется и не используется повторно
Вместе с ключом проекта это id для людей вида `WEB-12`

### Версия задачи

У задачи есть `version`
Растет при любом изменении задачи
Перемещение требует `version`
Если версия устарела сервер отвечает 409
Так при одновременном перемещении карточки не теряются

### Срок

`dueDate` это календарная дата без времени
Сервер не проверяет что она в будущем
Просрочку фронт считает сам по часовому поясу юзера

## Формы задачи

### Карточка

Приходит на доске в списках и в событиях сокета

```json
{
  "id": "uuid",
  "number": 12,
  "title": "Починить логин",
  "columnId": "uuid",
  "status": "in_progress",
  "position": 1024,
  "priority": "high",
  "dueDate": "2026-11-20",
  "assignee": { "id": "uuid", "displayName": "Даня", "avatarUrl": null },
  "blocked": false,
  "checklist": { "done": 1, "total": 3 },
  "version": 5
}
```

`assignee` равен `null` если исполнителя нет
`dueDate` равен `null` если срока нет

### Полная задача

Приходит в карточке задачи и после изменений

```json
{
  "id": "uuid",
  "projectId": "uuid",
  "number": 12,
  "title": "Починить логин",
  "description": "Текст в **markdown**",
  "columnId": "uuid",
  "status": "in_progress",
  "position": 1024,
  "priority": "high",
  "dueDate": "2026-11-20",
  "assignee": { "id": "uuid", "displayName": "Даня", "avatarUrl": null },
  "author": { "id": "uuid", "displayName": "Сережа", "avatarUrl": null },
  "blocked": true,
  "block": {
    "reason": "Ждем API от бэкенда",
    "by": { "id": "uuid", "displayName": "Даня", "avatarUrl": null },
    "at": "2026-11-13T12:00:00Z"
  },
  "checklist": [
    { "id": "uuid", "text": "Сверстать форму", "done": true, "position": 1 },
    { "id": "uuid", "text": "Написать тесты", "done": false, "position": 2 }
  ],
  "sourceMessageId": null,
  "createdAt": "2026-11-13T10:00:00Z",
  "updatedAt": "2026-11-13T12:00:00Z",
  "version": 5
}
```

`block` равен `null` если задача не заблокирована
`description` это markdown
Сервер хранит и отдает его как есть
Фронт рисует его тем же компонентом что и сообщения чата
`sourceMessageId` пока всегда `null`
Он появится когда будет чат и задачи из сообщений

## Доска

| Метод | Путь | Кто | Что |
|---|---|---|---|
| GET | `/projects/{projectId}/board` | участник | вся доска |
| GET | `/columns/{columnId}/tasks` | участник | догрузить задачи колонки |

### GET /projects/{projectId}/board

Фильтры в query
Все необязательные
Комбинируются через И

| Параметр | Тип | Смысл |
|---|---|---|
| assigneeId | uuid или `me` или `none` | задачи исполнителя. `none` это задачи без исполнителя |
| priority | TaskPriority | задачи с приоритетом |
| dueBefore | дата | срок не позже даты |
| dueAfter | дата | срок не раньше даты |
| blocked | `true` или `false` | только заблокированные или только нет |

Задачи без срока не проходят фильтры по сроку
Колонки приходят всегда
Фильтр убирает только задачи

```json
{
  "result": {
    "projectId": "uuid",
    "myRole": "member",
    "columns": [
      {
        "id": "uuid",
        "name": "Нужно сделать",
        "status": "todo",
        "position": 1,
        "tasksTotal": 132,
        "tasks": [],
        "nextCursor": "c2VjcmV0"
      }
    ]
  }
}
```

Колонки и задачи уже отсортированы по `position`
В `tasks` лежат карточки
`myRole` это роль текущего юзера в проекте
По ней фронт прячет кнопки управления колонками

В каждой колонке приходит не больше 50 задач
`tasksTotal` это сколько всего задач в колонке с учетом фильтров
`nextCursor` равен `null` если пришли все
Иначе остальные догружаются отдельным запросом
Так колонка Готово с тысячами задач не тормозит доску

### GET /columns/{columnId}/tasks

Параметры `cursor` и `limit`
Плюс те же фильтры что у доски
Ответ обычный список с пагинацией
В `items` лежат карточки

## Колонки

| Метод | Путь | Кто | Что |
|---|---|---|---|
| POST | `/projects/{projectId}/columns` | админ проекта | создать колонку |
| PATCH | `/columns/{columnId}` | админ проекта | переименовать или сменить статус |
| PUT | `/projects/{projectId}/columns/order` | админ проекта | переставить колонки |
| DELETE | `/columns/{columnId}` | админ проекта | удалить колонку |

### Колонка без задач

Приходит в ответах этого раздела и в событиях сокета

```json
{ "id": "uuid", "name": "Тестирование", "status": "review", "position": 5 }
```

### POST /projects/{projectId}/columns

```json
{ "name": "Тестирование", "status": "review" }
```

Оба поля обязательны
Колонка встает в конец доски
Ответ 201 колонка без задач

### PATCH /columns/{columnId}

```json
{ "name": "QA", "status": "review" }
```

Любое из полей
Смена статуса колонки меняет статус всех ее задач
В историю задач это не пишется
Ответ колонка без задач

### PUT /projects/{projectId}/columns/order

```json
{ "columnIds": ["uuid", "uuid", "uuid", "uuid"] }
```

Присылается полный список колонок доски в новом порядке
Не хватает колонки или есть чужая значит 400
Ответ список колонок без задач

### DELETE /columns/{columnId}?moveTasksTo={columnId}

Колонку с задачами без `moveTasksTo` удалить нельзя. Ответ 400
Задачи переезжают в конец колонки `moveTasksTo`
Переезд пишется в историю каждой задачи как `moved`
Последнюю колонку доски удалить нельзя. Ответ 400
Ответ `{ "result": { "id": "uuid" } }`

## Задачи

| Метод | Путь | Кто | Что |
|---|---|---|---|
| POST | `/projects/{projectId}/tasks` | участник | создать задачу |
| GET | `/tasks/{taskId}` | участник | полная задача |
| GET | `/projects/{projectId}/tasks/number/{number}` | участник | найти задачу по номеру |
| PATCH | `/tasks/{taskId}` | участник | изменить поля |
| POST | `/tasks/{taskId}/move` | участник | переместить |
| POST | `/tasks/{taskId}/block` | участник | заблокировать |
| DELETE | `/tasks/{taskId}/block` | участник | снять блокировку |
| DELETE | `/tasks/{taskId}` | автор или админ проекта | удалить |

### POST /projects/{projectId}/tasks

```json
{
  "title": "Починить логин",
  "description": null,
  "columnId": null,
  "assigneeId": "uuid",
  "priority": "high",
  "dueDate": "2026-11-20",
  "checklist": ["Сверстать форму", "Написать тесты"],
  "sourceMessageId": null
}
```

Обязателен только `title`
Без `columnId` задача попадает в первую колонку со статусом `todo`
Если такой колонки нет то в первую колонку доски
Задача встает в конец колонки
Исполнитель должен быть участником проекта. Иначе 400
Автор это текущий юзер
Ответ 201 полная задача

### GET /projects/{projectId}/tasks/number/{number}

Нужен для ссылок и упоминаний задачи по номеру
Ответ полная задача

### PATCH /tasks/{taskId}

```json
{
  "title": "Починить логин на мобилке",
  "description": "Новый текст",
  "assigneeId": null,
  "priority": "urgent",
  "dueDate": "2026-11-25"
}
```

Любые из этих полей
Колонку тут не меняют. Для этого есть move
`version` тут не нужна
Если двое меняют одно поле побеждает последний
Разные поля друг другу не мешают
Каждое изменение пишется в историю
Ответ полная задача

### POST /tasks/{taskId}/move

```json
{ "columnId": "uuid", "afterTaskId": "uuid", "version": 5 }
```

`afterTaskId` это задача под которой встанет перемещаемая
`null` значит в самый верх колонки
`afterTaskId` должна лежать в колонке `columnId`. Иначе 400
`afterTaskId` не может быть самой задачей. Иначе 400
Можно двигать внутри той же колонки
В историю пишется только смена колонки
Ответ карточка с новой позицией и версией

Если `version` устарела ответ 409
В `details` приходит актуальная карточка

```json
{
  "code": "CONFLICT",
  "message": "task was changed by someone else",
  "details": { "task": {} }
}
```

Фронт возвращает карточку на актуальное место
Юзер может повторить

### POST /tasks/{taskId}/block

```json
{ "reason": "Ждем API от бэкенда" }
```

Причина обязательна
Повторный вызов обновляет причину
Заблокированную задачу можно двигать и менять
Ответ полная задача

### DELETE /tasks/{taskId}/block

Тела нет
Задача не заблокирована значит 400
Ответ полная задача

### DELETE /tasks/{taskId}

Мягкое удаление
Задача пропадает с доски
История остается
После удаления задача отвечает 404
Ответ `{ "result": { "id": "uuid" } }`

## История задачи

| Метод | Путь | Кто | Что |
|---|---|---|---|
| GET | `/tasks/{taskId}/history` | участник | кто что и когда менял |

Пагинация по курсору
Новые сверху

```json
{
  "result": {
    "items": [
      {
        "id": "uuid",
        "action": "moved",
        "source": "user",
        "actor": { "id": "uuid", "displayName": "Даня", "avatarUrl": null },
        "before": { "columnId": "uuid", "columnName": "Нужно сделать", "status": "todo" },
        "after": { "columnId": "uuid", "columnName": "В работе", "status": "in_progress" },
        "createdAt": "2026-11-13T12:00:00Z"
      }
    ],
    "nextCursor": null
  }
}
```

`source` говорит откуда пришло изменение
`user` это действие человека
`github` это автопереход по PR
`system` это остальная автоматика
`actor` равен `null` если `source` не `user`
Так автопереходы видны в истории как требует ТЗ
Запись в историю и само изменение идут одной транзакцией
Записи в истории не меняются и не удаляются

### Что лежит в before и after

| action | before | after |
|---|---|---|
| `created` | `null` | `{ title, columnId, columnName }` |
| `title_changed` | `{ title }` | `{ title }` |
| `description_changed` | `{ description }` | `{ description }` |
| `assignee_changed` | `{ assignee }` | `{ assignee }` |
| `moved` | `{ columnId, columnName, status }` | `{ columnId, columnName, status }` |
| `priority_changed` | `{ priority }` | `{ priority }` |
| `due_date_changed` | `{ dueDate }` | `{ dueDate }` |
| `blocked` | `null` | `{ reason }` |
| `unblocked` | `{ reason }` | `null` |
| `checklist_changed` | `{ itemId, text, done }` | `{ itemId, text, done }` |
| `deleted` | `null` | `null` |

`assignee` тут это UserShort или `null`
`columnName` хранится в записи потому что колонку могут переименовать или удалить
У `checklist_changed` `before` равен `null` когда пункт добавили
А `after` равен `null` когда пункт удалили

## Realtime

Socket.io
Токен тот же что для HTTP
Передается при подключении в `auth.token`
Без токена или с плохим токеном подключение отклоняется

### Подписка на доску

Клиент шлет `board:subscribe`

```json
{ "projectId": "uuid" }
```

Сервер проверяет что юзер участник проекта
Ответ в ack

```json
{ "ok": true }
```

Нет доступа

```json
{ "ok": false, "code": "NOT_FOUND" }
```

Отписка через `board:unsubscribe` с тем же телом

### События от сервера

| Событие | Данные | После какого запроса |
|---|---|---|
| `task:created` | `{ task, actorId }` | создание задачи |
| `task:updated` | `{ task, actorId }` | PATCH задачи блокировка чеклист |
| `task:moved` | `{ task, fromColumnId, actorId }` | move |
| `task:deleted` | `{ taskId, columnId, actorId }` | удаление задачи |
| `tasks:reordered` | `{ columnId, positions: [{ taskId, position }] }` | сервер пересчитал позиции колонки |
| `column:created` | `{ column, actorId }` | создание колонки |
| `column:updated` | `{ column, actorId }` | PATCH колонки |
| `column:deleted` | `{ columnId, movedToColumnId, actorId }` | удаление колонки |
| `columns:reordered` | `{ columnIds, actorId }` | перестановка колонок |
| `board:access_revoked` | `{ projectId }` | юзера убрали из проекта |

`task` здесь это карточка
`column` это колонка без задач
`actorId` равен `null` у системных действий

### Правила

Все изменения идут через HTTP
Сокет только рассылает что уже записано в базу
Автор изменения получит и HTTP ответ и событие
Фронт сравнивает `version` и берет новее
После переподключения фронт заново подписывается и грузит доску через GET
После `column:deleted` и смены статуса колонки фронт тоже перезагружает доску
Юзера убрали из проекта значит сервер сразу убирает его из комнаты
Перед этим он получает `board:access_revoked`
